## 1. Методологія профілювання
Для аналізу продуктивності інформаційної системи було використано інструмент **VisualVM 2.2.1**.
**Параметри тестування**:
* **Інструмент**: CPU Sampler (Sampling mode).
* **Тестове оточення**: База даних PostgreSQL з наповненням у 10,000 записів товарів.
* **Сценарій**: Виконання 20 інтенсивних запитів пошуку за підрядком через API-ендпоїнт `/api/products/search`.

## 2. Базові метрики та "гарячі точки" (до оптимізації)
Згідно з початковими вимірами:
* **Метод `ProductService.searchProducts()`**: час виконання ~882 мс.
* **Метод `ProductResponseDTO.<init>`**: час мапінгу ~193 мс (24.6% CPU self-time).
* **Загальний час обробки запиту (Tomcat thread)**: до 1572 мс.

**Виявлені проблеми:**
1. **Проблема N+1**: Для кожного товару у списку система робила окремі запити в БД для отримання назви категорії та локації.
2. **Високі витрати на серіалізацію**: Формування великих JSON-відповідей через Jackson займало до 294 мс.
3. **Відсутність індексів**: Пошук виконувався шляхом повного сканування таблиці (Full Table Scan).

## 3. Реалізовані методи оптимізації
1. **Оптимізація JPQL (Eager Fetching)**: Впроваджено `JOIN FETCH` у `ProductRepository`, що дозволило отримувати всі пов'язані дані за один SQL-запит.
2. **База даних**: Створено B-tree індекси на поля `name` та `article` для прискорення текстового пошуку:
   `CREATE INDEX idx_products_search ON products (LOWER(name), LOWER(article));`
3. **Spring Cache**: Впроваджено кешування результатів пошуку на рівні сервісу для ідентичних запитів.
